# 团队子模块论文 Overrides

**适用条件**：步骤 4 团队 Gate 答 yes 时，本文件的 patch 应用于 engineering-30.md / academic-30.md。

**文件结构**：每个 patch 含：原条目 ID、原规则、override 后规则、判定示例。

---

## Patch 1：UND-RED-3（六要素缺失）— 工程型团队论文

**原规则**：六大要素缺一不可（缺一就红线）；要素可以章、节或子节形式承载。

**Override 后规则**：
- 团队子模块论文的"系统架构"要素允许以下三种合规形态（任一即可，不算红线）：
  1. **本论文自含整体系统架构**（最常见，王铭嵩采用）：在 §X 写出整个团队系统的总体架构图、功能架构图，
     然后在后续章节聚焦本人模块的详细设计。**这是最推荐的形态**——不依赖团队报告，独立可读。
  2. **本论文含本人模块局部架构 + 引用团队报告**：在 §X 给出本人模块的局部架构（≥ 3 页或含模块定位图），
     在摘要/绪论/架构章节中**显式声明**引用团队报告（grep 'XX 团队'、'本团队'、'详见团队报告'）。
  3. **本论文含团队整体简略架构 + 本人模块详细架构**：折中形态，先简述系统级架构，再详述模块级架构。
- 三种形态都不满足 → 仍为红线（要素缺失 + 未声明引用 = 真的缺）。
- 注意：架构要素可以是独立章，也可以是某章下的一节（如 §3.1 系统架构 + §3.2 本人模块设计）；只要内容承载够即可。

**判定示例**：
- 通过（形态 1）：§3.3 系统概要设计含整体功能架构图 + 系统架构图（整个团队系统级别），
  §4 详细设计聚焦本人模块。摘要中通过"系统由 X、Y、Z、W 模块构成 + 本论文聚焦 Y 模块"划界 → ✅
- 通过（形态 2）：§3 本人模块架构 共 5 页含模块定位图 + 显式引用团队报告 → ✅
- 通过（形态 3）：§3.1 整体架构（1 页简述）+ §3.2 本人模块详细架构 → ✅
- 警告→红线：架构要素全文不足 1 页且无任何系统级或团队级声明 → 🔴

## Patch 2：UND-ENG-B-04（技术后续被用）— 工程型 / 学术型团队论文

**原规则**：第 2 章每项技术须在后续被用，多余 = 冗余警告。

**Override 后规则**：
- 第 2 章介绍的技术只需在**本人负责模块的实现章**被使用即可。
- 多出的技术允许声明"由队友 X 实现，详见团队报告 §X.Y"，不算冗余。
- 但必须**明确声明**哪些技术由本人实现、哪些由团队其他成员实现，否则仍按冗余警告处理。

**判定示例**：
- 通过：第 2 章列了 Spring Boot、Vue、Redis、Docker；第 4 章实现章本人用 Spring Boot + Redis；架构章声明"Vue 前端由 X 同学负责（团队报告 §3.3）、Docker 部署由 Y 同学负责（团队报告 §3.5）" → ✅
- 警告：第 2 章列了 4 项，本人只用 2 项，但论文中无任何分工说明 → ⚠️（与原规则一致）

## Patch 3（新增）：UND-TEAM-DECL（团队归属声明）— 工程型 / 学术型团队论文

**这是新增条目，不替换任何已有条目。**

```yaml
id: UND-TEAM-DECL
类别: 团队论文专项
对应 PDF 要点: N/A（PDF 未涵盖团队场景，本 skill 补充）
问题: "团队子模块论文是否在摘要 / 绪论 / 系统概述中清晰划清本人模块与整体系统的边界"
说明: |
  基于 24-25 年优秀团队子模块论文实证（王铭嵩《SELABS 中综合资产管理模块的设计与实现》、
  严莹《全景光电感知系统目标跟踪模块的设计与实现》），优秀论文**不一定显式使用"团队"二字**，
  而是通过以下四种合规方式之一含蓄划界：

  ▸ 形式 1（显式团队声明）：直接写 "本论文为团队 XX 项目..."、"详见团队报告"
  ▸ 形式 2（系统列举）：写 "本系统主要由 X 模块、Y 模块、Z 模块、W 模块构成"，
    然后说明 "本论文主要设计实现 Y 模块"（王铭嵩采用的形式）
  ▸ 形式 3（系统名 + 模块名对偶）：摘要中并列出现 "整个系统名(SELABS)" 和 "本人模块名(综合资产管理模块)"，
    通过措辞自然划界 "...本系统..."、"...本文聚焦..."
  ▸ 形式 4（标题模式 — 最强证据）：论文标题本身已是 "<团队系统名> + <个人模块名>" 模式，
    例如 "SELABS 中综合资产管理模块的设计与实现"、"全景光电感知系统目标跟踪模块的设计与实现"。
    这种标题模式**仅凭题目就完成了划界**，团队归属一目了然。

  四种形式都能让评审清楚识别"团队整体 + 个人贡献边界"，**不必强求"团队"字面**。
  形式 4 是最简洁有力的形式，符合"题目即概要"的学术写作规范。
检查方法: |
  1. 在前 5 页（摘要 + 绪论 + 系统概述）grep `{team_project}` 字面量（步骤 4 用户填写的团队总项目名）
  2. 同时 grep `{my_module}` 字面量（用户填写的本人模块名）
  3. 划界形式判定（任一即视为合规）：
     - 形式 4（标题模式，最强证据，**优先检查**）：从 PDF 抽取论文标题，判断是否含
       {team_project} 与 {my_module} 字面量（或近似词），且呈"系统名 + 模块名"结构。
       命中即视为划界完成，可直接通过。
     - 形式 1：grep "团队|队友|分工|本团队|团队报告" ≥ 1 次
     - 形式 2：grep "本系统主要由.*?组成|本系统.*?构成|系统.*?四个模块|系统.*?N 个模块" ≥ 1 次，
       且 {my_module} 出现在该列举中
     - 形式 3：{team_project} 与 {my_module} 在前 5 页同时出现 ≥ 1 次，
       且摘要中能识别出"系统级 vs 模块级"措辞对偶（如"本系统..."、"本文..."、"主要设计实现"）
  4. 四种形式至少满足一种 → 通过
  5. 仅 {team_project} 或仅 {my_module} 命中（无对偶措辞、无系统列举、无团队字眼、无标题模式）→ 警告
  6. 都不命中 → 警告
评判标准:
  通过: 任一划界形式（团队字眼 / 系统列举 / 系统-模块对偶）满足
  警告: 仅命中部分关键词，但划界不清晰
  不合格: 不适用（本条最多警告）
修改建议模板: |
  "建议在论文标题、摘要或第三章 §3.1 增加划界说明（任选其一，标题模式最强）：
  - 标题模式（最强证据，最简洁）：把论文题目改写为 "{team_project} <介词> {my_module} 的设计与实现"，
    如 "SELABS 中综合资产管理模块的设计与实现"、"全景光电感知系统目标跟踪模块的设计与实现"。
    这种标题让团队归属一目了然，不必再额外声明。
  - 显式形式："本论文为团队 {team_project} 项目中 {my_module} 部分的设计与实现。
    团队整体由 N 名成员协作完成，团队整体设计详见团队报告。"
  - 系统列举形式（推荐，王铭嵩采用）："本系统主要由 X 模块、{my_module}、Y 模块和 Z 模块构成，
    本文主要设计和实现 {my_module}。"
  - 对偶形式（严莹采用）："{team_project} 通过整合... 形成... 本文设计并实现了 {team_project} 的 {my_module}..."
  四种形式都能让评审清楚识别团队边界与个人贡献。"
团队论文 override: N/A（本条本身是团队论文专项）
```
